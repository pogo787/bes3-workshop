# Proposal: load the PDF part-image map lazily

Status: **analysis only; not implemented in Batch 4.** This note responds to
finding M20 of `code-review.md` (`docs/internal/review/review-1/code-review.md`).

## Current state

- `index.html:140` loads `web/workshop/part-images-pdf.js` synchronously in the
  document head, before `report-pdf.js` and `ui.js`.
- The file is a single generated script. At the time of review it was 382,795
  bytes and contained base64 JPEG thumbnails for every part image.
- `web/workshop/report-pdf.js:470` reads the global
  `window.Bes3PartImagesPdf` when it builds a PDF.
- The normal UI does **not** use this map. It uses the much smaller
  `web/workshop/part-images.js` (`window.Bes3PartImages`) for the card images,
  and `web/parts/*.webp` for the image files.
- No generator for `part-images-pdf.js` exists in this tree. The file has a
  generated-file header but was not produced by a committed tool. That gap
  must be closed before regenerating it.

The cost is paid by every visitor on first load, including visitors who only
read the dashboard and never open the Report tab. No browser profiling was run
in this batch; the 383 KB figure is from the file size, not from a measured
first-paint delta.

## Options

| Option | Change | Benefit | Cost / risk |
| --- | --- | --- | --- |
| A. Dynamic script on first PDF build | Replace the eager `<script>` with a loader that injects `part-images-pdf.js` when the Report tab first builds a PDF | Smallest change; removes the map from initial parse | Still parses 383 KB as one script; the first PDF preview can pause; loader must handle failure and duplicate requests |
| B. Fetch a JSON map on first PDF build | Generate `part-images-pdf.json`, `fetch()` it once, keep it in memory | Removes the map from initial parse and from the JS bundle; browser can cache it | Report build becomes async; `file://` use needs a fallback; CSP needs `connect-src 'self'`; still transfers 383 KB on first use |
| C. Split by component and fetch on demand | Generate one JSON/JS chunk per component, fetch only the components present in the readout | Smallest transfer for a typical report | More generator and loader code; more failure states; not worth it before B exists |
| D. Keep it eager | No change | Simplest code | Leaves the M20 finding open for every visitor |

## Recommendation

Use **B** after adding a committed generator, with **A** as the fallback for
environments where `fetch()` of a local JSON file is blocked.

1. Add the missing generator (or document the exact one-off process) so the
   map is reproducible from `web/parts/*.webp`.
2. Emit `web/workshop/part-images-pdf.json` instead of a JS assignment.
3. Load it only when the Report tab is opened or a PDF build is requested.
   Cache the parsed object in memory and share one in-flight promise.
4. Keep `part-images.js` eager: it is small and the card images are part of the
   normal read view.
5. On load failure, render the existing placeholder/icon path and show a
   non-blocking message; do not fail the whole report.
6. If `fetch()` fails because the page is opened from `file://`, fall back to a
   dynamic `<script>` that loads the old JS map (kept as a compatibility file
   for one release).

## Acceptance criteria

- `index.html` no longer loads the 383 KB map before first paint.
- The Report tab and both PDF actions still produce the same images.
- A failed map load leaves the rest of the report usable and explains the
  missing thumbnails.
- The map can be regenerated by a committed script from `web/parts/*.webp`.
- No network access is required for a normal read; the JSON is same-origin.

## Out of scope

- Changing the PDF layout or jsPDF version.
- Optimising the WebP images themselves.
- Moving the map into a service worker or build pipeline.
